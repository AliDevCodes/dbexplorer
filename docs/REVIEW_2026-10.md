# Architecture review and refactor plan (2026-10-25)

Scope of this review: `PROJECT_MASTER_CONTEXT.md`, `ARCHITECTURE.md`, `CODE_MAP.md` (headers), the solution structure, and the code of the map, monitoring, export, credential and explorer view models that were changed in this phase. Files not read line by line are listed in §6 as **not reviewed**.

## 1. Summary
The layering idea is sound: Domain, Application (contracts), Infrastructure (I/O), Wpf (composition and UI). The main problems are not in the layers but in **three places**:
1. **Big view models with many partial files** (`MapViewModel`, `TableQueryViewModel`, `MonitoringViewModel`). They mix state, I/O orchestration, UI messages and layout rules.
2. **Two-way bindings on derived state** (the cause of the crash loop, N1) and **nulls from controls** (N2).
3. **No ViewModel tests.** Every serious bug of this phase was visible only in the running UI.

Second-order problems: presentation data in Domain, a serializer attribute in Domain, one class implementing two writer contracts, and a few places where UI code calls into Infrastructure types directly.

## 3. What is good and should stay
- Read-only guard, typed parameters, server-side paging: correct and central.
- `CoordinateRules` / `MapLayer` invariants in the constructor: good pattern, keep.
- Atomic JSON writes (temp file + move) in the layer and monitor stores.
- `CsvPartsWriter` cleanup on failure/cancel.
- Credential flow: vault first, profile flag second; no password in profile JSON.
- Single persistent map view with explicit release (after N3 fix).

## 4. Refactor plan (phased, each phase needs owner approval)
Each phase is one or more commits; each commit must build, pass tests, and carry its own checklist. No phase changes runtime behaviour unless stated.

### Phase R1 — Safety net (no behaviour change) · risk: low
- Add a test project section `tests/FastDbExplorer.Tests/ViewModels/` (xUnit, no UI thread: use `Dispatcher`-free view models or `[STAThread]` only where needed).
- Tests first for: `MapViewModel` tab state (N1), `FilterRowViewModel` null operator (N2), `ConnectionViewModel` password state machine, `TableQueryViewModel.TryBuildRequest` (filters, order, keyset requirements), `MonitoringViewModel` selection count, `MapViewModel.ShowQueryResultLayer` duplicate rule.
- Goal: 20–30 tests that describe current behaviour. Refactors in later phases must keep them green.

### Phase R2 — Move presentation out of Domain · risk: low–medium
- Create `Wpf/Presentation/` (or `Assets`-side static data) for `MapMarkerCatalog` palette and path data and `MapSourceStyles` colours/glyphs.
- Move `PersianDateTimeCodec` to `Wpf/Localization` or `Wpf/Presentation`; Domain keeps `DateTime` only.
- Replace `[JsonIgnore]` in Domain with DTO mapping inside Infrastructure (`JsonConnectionProfileStore` and `JsonMonitorStore` already have DTO shapes or can get them).
- Tests: `MapMarkerCatalogTests` and `MapSourceStylesTests` move with the code; behaviour identical.

### Phase R3 — Split the big view models · risk: medium
- `MapViewModel` → `MapDocumentViewModel` (open file, layers, camera, status), `CoordinateLayersViewModel` (Excel/manual layers, styles, radius), `MapResultsViewModel` (query result sets), `MapToolsViewModel` (my points, selection cards). Shared state through a small `MapSession` object, not through the parent class.
- `TableQueryViewModel` → `QueryFilterBuilder` (plain class: rows → `FilterCondition`s, testable), `PagingController` (cursor stack, keyset rules), `MapSendCoordinator` (rows → `QueryMapPoint`s, column checks), `ExportCoordinator`.
- Each new class is testable without UI; ViewModels become thin.
- Commit per extracted class; tests from R1 stay green after each commit.

### Phase R4 — One binding policy across the UI · risk: medium
- Audit every `TwoWay` binding in `Views/*.xaml`. Rule: TwoWay only for user input fields (text boxes, check boxes with no derived meaning). Everything derived becomes OneWay + a command.
- Introduce a `ViewState` pattern where a view has more than two related flags (idle, loading, empty, error, ready).
- Tests: state transitions for the changed view models.

### Phase R5 — Composition and module registration · risk: low
- Split `App.xaml.cs` registrations into `Infrastructure/ServiceRegistration.cs` (`AddFastDbInfrastructure`) and `Wpf/CompositionRoot.cs` (`AddFastDbUi`).
- Register writers explicitly: one registration per interface; no casts in the composition root (F9).
- Store paths in one `AppPaths` class (connections, credentials, layers, monitors, logs, WebView2 folder).

### Phase R6 — Map JavaScript modules · risk: medium
- Split `coordinate-layers.js` into `layers.js` (sources, markers), `selection.js` (hover, click, highlight) and `tooltip.js`.
- Split `map-tools.js` into `tools-geo.js` (parsing, distance — pure functions), `tools-ui.js` (cards, chips), `tools-measure.js`.
- Pure functions (parse coordinates, haversine, label formatting) can be tested with a small Node script in `tests/js/` (not part of the .NET build). Add a static check: every `post({type})` used in JS has a `case` in C#.

### Phase R7 — Dependencies · risk: low
- Pin all NuGet versions after the next successful restore; record them in `Directory.Packages.props` (central package management).
- Resolve the Pkcs advisory (explicit reference to a fixed version or a newer SqlClient).
- Remove `Microsoft.Extensions.Hosting` only if the DI in R5 is simpler without it; decide after R5, not before.

## 5. Order and rationale
R1 first (without tests every later step is guesswork). R2 and R5 are low risk and make the next steps clearer. R3 and R4 are where most bugs hide, so they come after R1. R6 is independent and can run in parallel with R3. R7 at the end.
